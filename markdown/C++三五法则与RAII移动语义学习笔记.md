# C++ 资源所有权：RAII、三/五法则与移动语义

> 本文为 M1 的 Shader 类设计服务。Shader 持有 GL 程序句柄（GLuint），必须先想清楚"这个对象能不能被复制"，否则会出双重释放。

---

## 一、问题从哪来：谁负责销毁 GL 程序

你的 Shader 类里会存一个 `GLuint`（着色器程序的句柄/编号）。程序结束时要调用 `glDeleteProgram(id)` 释放它。

问题来了：如果 Shader 对象被"复制"了（函数返回、放进容器、赋值），就会出现**两个对象持有同一个 GLuint**，最后两个对象都去 `glDeleteProgram` → **同一个程序被删除两次** → 未定义行为 / 崩溃。

这就是"资源所有权"问题：**一个资源，到底归谁负责释放？**

---

## 二、RAII：资源生命周期 = 对象生命周期

RAII（Resource Acquisition Is Initialization，资源获取即初始化）是 C++ 最核心的惯用法：

- **构造函数**里获取资源（Shader 构造时编译链接好程序）；
- **析构函数**里释放资源（Shader 析构时 `glDeleteProgram`）。

这样资源生命周期和对象生命周期绑定，对象销毁时资源自动释放，不会忘。

---

## 三、默认拷贝是"浅拷贝"，会双重释放

C++ 编译器会**默认生成**拷贝构造函数和拷贝赋值运算符，它们做的是"逐成员复制"（浅拷贝）：

- 对 `GLuint` 这种整数成员，就是简单复制数值；
- 结果：两个 Shader 对象的 `GLuint` 值相同，指向同一个 GPU 程序。

两个对象先后析构 → 同一个程序被 `glDeleteProgram` 两次 → 出问题。

---

## 四、三法则（Rule of Three）

> 如果类的成员里涉及"手动管理的资源"（指针、句柄、文件、锁……），而你又需要自定义**析构函数、拷贝构造、拷贝赋值**中的任意一个，通常三个都要自己定义，保持一致。

经典情景：一个管理 `char*` 的字符串类。

- 有析构函数 `delete[] buf`（释放资源）；
- 就必须有拷贝构造（深拷贝，复制一份新的 buf）；
- 必须有拷贝赋值（先释放旧的，再深拷贝新的）。

否则默认浅拷贝会让两个对象指向同一块 buf，析构时双重 `delete[]`。

---

## 五、移动语义：转移，而不是复制

有时候"复制"根本没意义——GPU 程序只有一个，你不想复制它。但你**希望把对象"移交"**给另一个对象（比如函数返回时）。

移动（move）就是：**把资源的所有权从"源对象"转移到"目标对象"，然后把源对象置空。**

- **移动构造**：新对象"抢走"源对象的资源，源对象变成空壳（GLuint 置 0 / 置无效值）。
- **移动赋值**：目标对象先释放自己的旧资源，再抢走源对象的资源。
- 移动之后，源对象仍然活着，但**不能再被正常使用**（它已经没有资源了）。

---

## 六、五法则（Rule of Five）

现代 C++（C++11 起）在"三法则"基础上加入两个移动操作，变成**五法则**：

1. 析构函数
2. 拷贝构造函数
3. 拷贝赋值运算符
4. 移动构造函数
5. 移动赋值运算符

**经验法则：这五个里，只要你需要自定义其中任意一个，就应该把这五个都写清楚**（要么都实现，要么明确用 `= delete` 禁用）。

---

## 七、零法则（Rule of Zero，进阶）

如果一个类的成员**自己已经正确管理了资源**（比如用 `std::string`、`std::vector`、`std::unique_ptr`，而不是裸 `char*` / 裸句柄），那你就**不需要**写五法则中的任何一个——让编译器默认生成即可。

这是 C++ 现代风格：**尽量让类"零法则"，把资源管理交给标准库容器和智能指针。**

---

## 八、回到 Shader 类：你真正要决策的是什么

理解了上面这些，决策 2 其实就问一个具体问题：

> **你的 Shader 对象，允不允许被"复制"或"移动"？**

可选方向（三选一）：

| 方向 | 含义 | 适用 |
|---|---|---|
| **A：禁拷贝 + 实现移动** | `= delete` 拷贝构造/赋值；手写移动构造/赋值（把 GLuint 转移、源置空） | 最常见，Shader 可以放进 vector 或作为函数返回值 |
| **B：禁拷贝 + 禁移动** | 全部 `= delete` | 最省事、最安全，但 Shader 对象"就地处死"，不能移动/返回 |
| **C：共享所有权（如 shared_ptr）** | 用智能指针共享同一个程序 | 不推荐，GPU 资源的共享语义容易踩坑，先别用 |

**你只需要告诉我：你想让 Shader 走 A、B、C 哪条路？** 选完之后，我才好进一步跟你讨论"移动构造具体怎么写"这类实现问题。
