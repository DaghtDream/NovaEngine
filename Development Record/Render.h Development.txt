问题：Render Capability 的职责边界是什么？它应该在哪一帧阶段执行？

--------------------------------------------------------------------------------
  1. 初始现状
--------------------------------------------------------------------------------

ICapabilities 提供三个生命周期钩子：
  OnAttach(Scene* scene)  → 接入场景
  OnDetach()              → 脱离场景
  OnUpdate(float dt)      → 每帧被 Scene::Update 调用

Scene::Update 当前的执行流程：
  for (cap in capabilities):   // 按优先级升序遍历
      cap->OnUpdate(dt)
  FlushCommand()               // 消费命令队列

--------------------------------------------------------------------------------
  2. 核心矛盾
--------------------------------------------------------------------------------

问题：Render::OnUpdate 和 FlushCommand 的执行顺序

如果 Render 在 FlushCommand 之前执行：
  - 本帧 PushCommand 创建的对象，Render 看不到
  - 本帧 PushCommand 销毁的对象，Render 还会渲染
  - 造成"逻辑与画面差一帧"的现象

如果 FlushCommand 在 Render 之前执行：
  - 需要修改 Update 的遍历顺序
  - 破坏了"优先级统一排序"的简单性

--------------------------------------------------------------------------------
  3. 讨论过的方案
--------------------------------------------------------------------------------

方案 A：保持现状，接受"逻辑滞后一帧"
  - 创建实体 ≠ 需要立即渲染，新对象下一帧可见
  - 帧内状态确定，可复现
  - 缺点：物理碰撞等场景下，对象已销毁但画面仍残留一帧

方案 B：修改 Update，让 Render 在 FlushCommand 之后
  - 需要重新设计遍历逻辑
  - 破坏现有优先级排序机制的简洁性

方案 C：Render 内部主动调用 FlushCommand
  - 单条渲染管线时可行
  - 多条渲染管线（ShadowMap、Deferred、PostProcess）时 FlushCommand 被反复调用
  - 架构上"消费者不应该决定同步时机"

--------------------------------------------------------------------------------
  4. 最终采用方案：基于优先级的两阶段更新
--------------------------------------------------------------------------------

将 Scene::Update 拆分为两个阶段：

  阶段一：逻辑更新（优先级 0~49）
  阶段二：渲染更新（优先级 100+）

中间以 FlushCommand 作为同步点。

伪代码：
  Scene::Update(dt):
      // 阶段一：逻辑
      for (cap in capabilities):
          if (cap->GetPriority() >= LOGIC_PRIORITY_MAX) break
          cap->OnUpdate(dt)
      
      // 同步点：消费所有逻辑阶段产生的命令
      FlushCommand()
      
      // 阶段二：渲染
      for (cap in capabilities):
          if (cap->GetPriority() < RENDER_PRIORITY_MIN) continue
          cap->OnUpdate(dt)

--------------------------------------------------------------------------------
  5. 优先级分区约定
--------------------------------------------------------------------------------

  0  ~ 49  ：逻辑阶段（Physics、AI、Script 等）
  50 ~ 99  ：预留缓冲带（统计、调试、中间处理等）
  100+     ：渲染阶段（Render、ShadowMap、PostProcess 等）

常量定义：
  constexpr int LOGIC_PRIORITY_MAX = 49;
  constexpr int RENDER_PRIORITY_MIN = 100;

Render Capability 的 GetPriority() 返回 100。

--------------------------------------------------------------------------------
  6. 方案优势
--------------------------------------------------------------------------------

  1. 零破坏性：不修改 ICapabilities 接口，所有现有 Capability 无需改动
  2. 利用现有基础设施：AddCapability 已按优先级排序，无需额外分组
  3. 预留扩展空间：50~99 缓冲区可容纳"非逻辑非渲染"的中间层 Capability
  4. 常量即文档：LOGIC_PRIORITY_MAX / RENDER_PRIORITY_MIN 明确表达了架构意图

--------------------------------------------------------------------------------
  7. 已知注意事项
--------------------------------------------------------------------------------

  1. OnDetach 销毁顺序：ClearAllCapabilities 从后往前删除，Render（优先级 100）
     在 vector 末尾，OnDetach 最先被调用。如果未来有逻辑 Capability 在 OnDetach
     中 PushCommand，该 Command 在 Render 已 delete 之后才产生，可能引发问题。
     当前无此场景，暂不处理。

  2. 阈值边界：50~99 区间的 Capability 既不参与阶段一也不参与阶段二，需要明确
     该区间的语义。当前预留为空，后续根据实际需求定义。

  3. 压力测试约束：CreateObject 后同一帧内 Render 不可见新对象，测试断言需要
     在创建后额外调用一次 Update 再验证。

--------------------------------------------------------------------------------
  8. 后续待讨论
--------------------------------------------------------------------------------

  （GameObject.transform + Mesh + PointLight）

  第三步：着色器资源生命周期 —— OnAttach/OnDetach 管理着色器

问题：Render::OnUpdate 需要三种数据（Transform + Mesh + PointLight），
      如何从 Scene 的 API 中高效获取？

--------------------------------------------------------------------------------
  1. 数据来源分析
--------------------------------------------------------------------------------

渲染一个物体需要：
  GameObject.position/rotation/scale  → 构建 model 矩阵
  Mesh.VAO/VBO/EBO/indexCount         → 画什么几何体
  PointLight.color                    → 用什么颜色

三个数据分布在 Scene 的不同容器中：
  GetObject()     → unordered_map<uint32_t, GameObject>
  GetPool<Mesh>() → unordered_map<uint32_t, any>     (通过 ForEach 访问)
  GetPool<PointLight>() → unordered_map<uint32_t, any> (通过 GetComponent 访问)

没有单一 API 能一次性返回全部三种数据。

--------------------------------------------------------------------------------
  2. 主循环选择：ForEach vs ID 遍历
--------------------------------------------------------------------------------

候选 A：以 Mesh 组件池为主循环（ForEach<Mesh>）
  - 只遍历有 Mesh 的对象
  - 每次迭代做 2 次 hash 查找（GetObject + GetComponent）
  - 场景有 10,000 对象、8,000 有 Mesh → 遍历 8,000 次

候选 B：以 GameObject 容器为主循环
  - 遍历所有对象
  - 每次迭代做 2 次 hash 查找（GetComponent<Mesh> + GetComponent<PointLight>）
  - 场景有 10,000 对象、8,000 有 Mesh → 遍历 10,000 次，2,000 次无效

选择：候选 A（ForEach<Mesh>）
  理由：只关心"能渲染的东西"，跳过无 Mesh 的对象。ForEach 的多组件交叉查询
  时，最小池遍历策略效率远优于全量 ID 遍历。

--------------------------------------------------------------------------------
  3. 数据获取流程
--------------------------------------------------------------------------------

ForEach<Mesh> 回调中：
  1. GetObject().at(id)         → GameObject& → position/rotation/scale
  2. GetComponent(id, lightPtr) → PointLight* → color（可能为 nullptr）
  3. 构建 model 矩阵：
     model = glm::translate(mat4(1.0), position)
           * glm::mat4_cast(rotation)
           * glm::scale(mat4(1.0), scale)
     （TRS 顺序：先缩放，再旋转，最后平移）

--------------------------------------------------------------------------------
  4. 决策总结
--------------------------------------------------------------------------------

  - 主循环：ForEach<Mesh>
  - 补充查询：GetObject() + GetComponent<PointLight>
  - 不新增 API：当前阶段不添加 ForEachWithObject 等合并查询 API
  - 两次 hash 查找的开销在当前规模下可接受，优化放在测试后

--------------------------------------------------------------------------------
  5. 已知限制
--------------------------------------------------------------------------------

  - GetObject() 暴露内部 unordered_map 引用，理论上外部可绕过 CreateObject/DestroyObject
    直接操作。当前不处理，属于 API 设计层面的后续优化项。
  - 无防御代码：Render 假设 ForEach 返回的 id 在 GetObject() 中一定存在。
    正常流程中 DestroyObject 同时清理组件池和对象 map，不会出现不一致。

问题：着色器（编译、链接、销毁）应该放在哪个生命周期？源码如何管理？

--------------------------------------------------------------------------------
  1. OnAttach/OnDetach vs 构造/析构
--------------------------------------------------------------------------------

构造/析构的问题：
  - new Render() 在 main.cpp 的哪一行执行决定了 OpenGL 上下文是否存在
  - 如果写在 glfwMakeContextCurrent 之前，glCreateShader 会失败

OnAttach/OnDetach 的优势：
  - SceneBegin() 在 main.cpp 里 glfwMakeContextCurrent 之后执行，上下文一定有效
  - 资源生命周期与 Scene 的接入/脱离天然绑定
  - 不依赖 Render 实例创建位置的代码顺序

决策：着色器资源放在 OnAttach / OnDetach 中管理。

--------------------------------------------------------------------------------
  2. 着色器源码管理：hardcode vs 文件加载
--------------------------------------------------------------------------------

hardcode 的问题：
  - main.cpp 第68-97行就是 hardcode 的着色器字符串
  - 随着着色器复杂度增加，C++ 源码中的字符串难以维护
  - 无法在运行时替换着色器进行调试

文件加载的优势：
  - 着色器作为资产独立管理，与 C++ 代码分离
  - 运行时可热重载（后续优化项）
  - 这是正经游戏引擎的标准做法

决策：从文件加载，一步到位。

--------------------------------------------------------------------------------
  3. 着色器文件位置
--------------------------------------------------------------------------------

目录：f:\NovaEngine\shader\（已有空文件夹）

文件：
  shader/default.vert   — 顶点着色器
  shader/default.frag  — 片元着色器

--------------------------------------------------------------------------------
  4. 运行时路径问题
--------------------------------------------------------------------------------

问题：exe 运行时的当前工作目录不固定（双击 vs VS调试 vs 命令行），
      导致相对路径可能失效。

解决方案：CMake 在编译时将 shader/ 文件夹拷贝到编译输出目录。

  file(COPY ${CMAKE_SOURCE_DIR}/shader/
       DESTINATION ${CMAKE_BINARY_DIR}/shader/)

效果：
  out/build/x64-Release/
  ├── shader/
  │   ├── default.vert   ← CMake 自动拷贝
  │   └── default.frag
  └── NovaEngine.exe

代码中使用 "shader/default.vert" 始终有效，因为两者始终在同一目录。

--------------------------------------------------------------------------------
  5. 文件 I/O 与错误处理
--------------------------------------------------------------------------------

OnAttach 中需要新增文件读取逻辑（fopen/fread 或 ifstream）。
目前项目无任何文件 IO 代码。

错误处理策略：文件读取失败直接报错，不做静默降级。
  - 着色器文件不存在或读取失败时，打印错误信息并终止程序
  - 不使用 fallback 硬编码着色器，保证"要么全有要么全无"的一致性

--------------------------------------------------------------------------------
  6. 决策总结
--------------------------------------------------------------------------------

  - 着色器生命周期：OnAttach（编译+链接）/ OnDetach（销毁）
  - 源码管理：文件加载，从 shader/ 文件夹读取
  - CMake 配置：file(COPY) 将 shader/ 拷贝到编译输出目录
  - 错误处理：无 fallback，读取失败即报错退出

问题：10,000 个对象如何共用 GPU 顶点数据？如何管理 VAO/VBO/EBO 的生命周期？

--------------------------------------------------------------------------------
  1. 批量渲染的两个层度
--------------------------------------------------------------------------------

层度一：共享顶点数据，每帧仍多次 Draw Call
  - 所有对象共用同一份 VAO/VBO/EBO
  - CPU 每帧仍需 10,000 次 Draw Call
  - Draw Call 开销成为瓶颈，干扰 ECS 遍历性能测量

层度二：真正的 Instanced Drawing
  - 所有对象共用同一份 VAO/VBO/EBO
  - CPU 每帧更新一次 instance buffer（10,000 个 model 矩阵）
  - glDrawElementsInstanced × 1
  - Draw Call 降至 1 次，真正分离出 ECS 遍历纯开销

决策：先做层度一，后续优化阶段做层度二。两个阶段数据可形成对照。

--------------------------------------------------------------------------------
  2. 共享 VAO 的存放位置
--------------------------------------------------------------------------------

方案 A：Mesh.VAO 字段就是共享数据
  - CreateQuadMesh() 多次调用，结果存入每个对象的 Mesh.VAO
  - 各 Mesh.VAO 存的值相同（都指向 GPU 中同一 VAO）
  - 各 Mesh.VAO 是独立变量（10,000 × 4 bytes，忽略不计）
  - DestroyObject 不调用 glDeleteVertexArrays，GPU 资源在程序退出时由 OS 回收

方案 B：Render 持有独立的共享 VAO/VBO/EBO
  - OnAttach 时创建共享 VAO，OnDetach 时销毁
  - Render::OnUpdate 用自己持有的 VAO，不读写 Mesh.VAO
  - Mesh.VAO 字段在当前阶段实际无意义
  - 需要重构 Scene/Component 代码以支持共享资源管理

决策：方案 A。一切需要重构代码的操作往后放。

--------------------------------------------------------------------------------
  3. GPU 资源生命周期
--------------------------------------------------------------------------------

  - 创建：在 main.cpp（或未来的对象创建函数）中调用 CreateQuadMesh()
  - 共享：所有对象的 Mesh.VAO 指向同一份 GPU 数据
  - 销毁：DestroyObject 不删除 GPU 资源
  - 清理：程序退出时由操作系统回收（Windows 进程结束时自动释放 OpenGL 资源）

--------------------------------------------------------------------------------
  4. CreateQuadMesh 的归属
--------------------------------------------------------------------------------

CreateQuadMesh() 放在 Render 类中作为静态方法。
理由：
  - OpenGL 调用集中在一处，不散落在 Scene 或 Component 代码中
  - 将来如果要支持不同几何体，CreateCubeMesh() / CreateSphereMesh() 同样放在 Render
  - Render 负责所有 GPU 资源的管理

--------------------------------------------------------------------------------
  5. 决策总结
--------------------------------------------------------------------------------

  - 批量渲染阶段：层度一（多次 Draw Call），层度二（Instanced）留作优化
  - VAO 存放位置：Mesh.VAO 字段，不做共享资源管理重构
  - GPU 资源清理：不主动释放，依赖 OS 进程退出回收
  - CreateQuadMesh：Render 类的静态方法
